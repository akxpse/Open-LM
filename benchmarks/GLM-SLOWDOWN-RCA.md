# GLM slowdown: root-cause analysis

2026-09-13. Investigation uses existing event timestamps and LM Studio performance logs; no new inference, implementation or test result was generated by this analysis.

## Confirmed time breakdown

| Component | Qwen seconds | GLM seconds |
| --- | ---: | ---: |
| Auxiliary title generation, prompt + decode | 1.229 | 27.404 |
| Four worker requests: prompt processing | 8.979 | 9.854 |
| Four worker requests: generation | 8.135 | 40.645 |
| Remaining wall time outside summed runtime reports | 2.410 | 1.630 |
| Observed whole run | 20.753 | 79.533 |

Rounding can affect sums. Runtime reports are sequential at parallel=1. Residual wall time is not an independently instrumented component; it includes client/setup/transport gaps and measurement rounding. Model load time is excluded from both run durations.

The roughly 58.8-second difference is principally extra title time (~26.2 s) and extra worker decoding time (~32.5 s), not slower tests or dramatically slower prompt ingestion. Node's own TAP report measured about 75 ms for Qwen's tests and 59 ms for GLM's.

## Root causes and uncertainty

1. **Confirmed auxiliary overhead.** Both runs invoked OpenCode's title generator, routed to the same local model as their worker. The server request explicitly says it is generating a conversation title. GLM decoded 949 tokens for it versus Qwen's 9. At parallel=1 the first worker request waited for that title generation. This adds real latency even though the runner does not emit a worker step for the title. The exact reasoning/content split of those auxiliary tokens was not captured; do not label all 949 reasoning tokens.
2. **Confirmed extra worker generation.** GLM's worker reported 232 output plus 253 reasoning tokens; Qwen reported 255 output and zero reasoning. Reasoning is enabled by GLM's selected model manifest. This explains additional generation work, but not the entire generation-time gap.
3. **Confirmed late throughput collapse; deeper cause UNKNOWN.** Server decoding reports for GLM's worker moved from 29.71 to 21.46 to 3.05 to 2.94 tokens/second across its four requests. Qwen stayed around 29–31 tokens/second. The two slow GLM requests produced only 50 and 23 tokens, so their delay cannot be explained by output length alone. Existing evidence does not distinguish scheduler/GPU contention, runtime behavior, power/thermal effects or another cause. The later thermal query had no recorded warning; it is not historical proof that no throttling occurred.
4. **RAM overload not established.** Swap did not grow in the sampled GLM run, and the final memory-pressure query showed 34% free. No OOM or load failure occurred for the tested community GGUF. Sparse snapshots are not a peak-memory or long-duration stability test.

The prior MLX load guardrail failure is a separate setup incident. It does not explain the successful GGUF's inference timing. No evidence supports claiming OpenCode tool parsing failed here: both models completed native read/edit/bash and stopped normally.

## Token accounting correction

[Performance records](GLM-QWEN-PERFORMANCE.json) contain all five server requests per model.

| Measurement boundary | Qwen | GLM |
| --- | ---: | ---: |
| Worker API step input | 15,003 | 14,834 |
| Worker output + reasoning | 255 | 485 |
| Worker API step total | 15,258 | 15,319 |
| All-request runtime decoded tokens, including title | 264 | 1,434 |
| All-request newly evaluated prompt tokens | 3,962 | 4,282 |

Different counter boundaries must not be added together. Runtime prompt evaluation excludes already-reused prefixes, while worker API input counters include repeated context. Runtime decoding can include special tokens. Full API input/output usage for auxiliary requests is unknown; its absence is not zero. The earlier nearly-equal worker totals do not demonstrate nearly-equal full workflow usage.

Local token consumption is acceptable if it improves results without destabilizing memory or sustained throughput. These counts are diagnostics, not cloud-cost savings or a reason by themselves to reject GLM.

## Provisional verdict

- Quality: tied on the two-test utility; Qwen omits one redundant type check. Insufficient evidence for a general quality winner, especially on long/multi-file work.
- Speed: Qwen won in this observed configuration. Do not generalize the 3.83x wall-time ratio as an intrinsic model speed ratio.
- Tokens: Qwen generated fewer runtime tokens across the entire observed workflow; the initial worker-only summary understated GLM's auxiliary work.
- Long-running use: neither model is certified by this experiment. Prefer the currently demonstrated Qwen workflow provisionally, while keeping GLM as a candidate for controlled testing. Required priority is accepted quality, stable RAM/swap and sustained throughput; local token counts are secondary.
